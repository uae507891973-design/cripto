# План реализации: спот grid-бот для Bybit (Python + pybit)

> Базовый документ: [PLAN.md](PLAN.md) — общий план, безопасность, условия
> интеграции. Здесь — конкретная реализация.
>
> Принятые решения (можно пересмотреть до M2): стратегия v1 — **grid на
> споте**, стек — **Python 3.11+ и официальный SDK `pybit`**, стейт —
> **SQLite**, деплой — **Docker на VPS**. DCA добавляется в v2 как второй
> модуль стратегии поверх того же ядра.

---

## Целевая структура проекта

```
cripto/
├── bot/
│   ├── config.py          # загрузка конфига + секретов из env, валидация (pydantic)
│   ├── exchange/
│   │   ├── client.py      # обёртка над pybit: подпись, retry, rate-limiter
│   │   ├── market_ws.py   # публичный WS: тикеры/стакан
│   │   └── private_ws.py  # приватный WS: order/execution/wallet
│   ├── core/
│   │   ├── models.py      # Order, Fill, GridLevel, Position (dataclasses)
│   │   ├── state.py       # SQLite-хранилище состояния, журнал сделок
│   │   └── reconcile.py   # сверка локального состояния с биржей
│   ├── strategy/
│   │   ├── base.py        # интерфейс стратегии (on_tick, on_fill, desired_orders)
│   │   └── grid.py        # grid-логика: уровни, перестановка ордеров
│   ├── risk/
│   │   └── manager.py     # лимиты позиции/убытка, kill-switch, автостоп
│   ├── execution/
│   │   └── engine.py      # diff желаемых/реальных ордеров → create/cancel
│   ├── monitoring/
│   │   ├── telegram.py    # алерты и команды (status, stop)
│   │   └── health.py      # heartbeat, метрики
│   └── main.py            # запуск, wiring, graceful shutdown
├── backtest/
│   ├── data.py            # загрузка klines /v5/market/kline
│   └── runner.py          # прогон grid-стратегии по истории
├── tests/                 # pytest: unit + интеграционные (mock API)
├── config.example.yaml    # шаблон конфига (без секретов)
├── .env.example           # BYBIT_API_KEY=..., BYBIT_API_SECRET=...
├── Dockerfile
├── docker-compose.yml
└── .pre-commit-config.yaml  # gitleaks, ruff, mypy
```

## M0. Каркас проекта (1–2 дня)

**Готово, когда:** `docker compose run bot --help` работает, CI зелёный.

- [ ] Инициализация: `pyproject.toml` (Python 3.11+), зависимости: `pybit`,
      `pydantic`, `websocket-client`, `python-telegram-bot`, `pytest`, `ruff`, `mypy`.
- [ ] Скелет модулей по структуре выше, точка входа `bot/main.py` с CLI
      (`--mode demo|testnet|mainnet`, `--dry-run`).
- [ ] `.gitignore` (`.env`, `*.db`, логи), `.env.example`, `config.example.yaml`.
- [ ] pre-commit: **gitleaks** (секреты не попадают в git), ruff, mypy.
- [ ] GitHub Actions: lint + tests на каждый push.
- [ ] Dockerfile (non-root user) + docker-compose с `env_file`.

## M1. Слой биржи (3–5 дней)

**Готово, когда:** интеграционный скрипт на demo-среде получает баланс,
ставит и отменяет лимитный ордер, а rate-limiter не допускает 403.

- [ ] `exchange/client.py` — обёртка над `pybit.unified_trading.HTTP`:
  - выбор базового URL по режиму: `api-demo.bybit.com` / `api-testnet.bybit.com`
    / `api.bybit.com`;
  - методы: `get_balance`, `get_instrument_info` (шаг цены/лота, min notional),
    `place_limit`, `cancel`, `cancel_all`, `open_orders`, `get_klines`;
  - каждый ордер — со своим `orderLinkId` (uuid): идемпотентность;
  - обработка `retCode` (карта известных кодов: 10006 rate limit,
    170131 insufficient balance, и т.д.) + экспоненциальный retry
    только для сетевых/5xx ошибок, **не** для бизнес-отказов;
  - клиентский rate-limiter (token bucket) с запасом ~20% от лимитов Bybit:
    ≤16/с create, ≤16/с cancel, глобально ≤480 запросов/5 с;
  - чтение заголовков `X-Bapi-Limit-Status` → лог при остатке <20%.
- [ ] Синхронизация времени: при старте и раз в час сверка с
      `/v5/market/time`; при дрейфе > recv_window/2 — алерт.
- [ ] Unit-тесты: подпись/параметры (мок HTTP), retry-политика, rate-limiter.

## M2. Состояние и модели (2–3 дня)

**Готово, когда:** перезапуск процесса восстанавливает картину ордеров без
дублей и потерь (проверено тестом).

- [ ] `core/models.py`: `GridLevel(idx, price, side, qty, order_link_id, status)`,
      `Fill`, `BotState`.
- [ ] `core/state.py`: SQLite (WAL) — таблицы `orders`, `fills`, `pnl_journal`,
      `bot_meta`. Каждая сделка пишется в журнал (основа налогового учёта).
- [ ] `core/reconcile.py`: при старте и каждые N минут — сравнение локальных
      ордеров с `open_orders()` биржи; расхождение = алерт + приведение
      локального состояния к биржевому (биржа — источник истины).

## M3. Grid-стратегия (3–5 дней)

**Готово, когда:** бэктест на годовой истории BTCUSDT воспроизводит ожидаемую
механику (каждый fill порождает встречный ордер), метрики сходятся вручную.

- [ ] `strategy/grid.py`:
  - параметры: пара, нижняя/верхняя граница, число уровней (арифметическая /
    геометрическая сетка), объём на уровень, размер общего капитала;
  - инициализация: расчёт уровней, стартовая закупка базового актива под
    sell-уровни выше цены;
  - реакция на fill: исполнился buy на уровне i → выставить sell на уровне
    i+1 (и наоборот);
  - округление цены/объёма по `instrument_info` (tickSize, basePrecision,
    minOrderAmt) — обязательный тест;
  - поведение при выходе цены из диапазона: режим `hold` (ничего не делать)
    или `stop` (cancel-all + алерт) — по конфигу.
- [ ] `backtest/runner.py`: прогон по klines c учётом комиссии (параметр
      конфига, ⚠ актуальное значение взять из аккаунта) и допущением
      «fill при касании уровня». Отчёт: PnL, число сделок, макс. просадка,
      сравнение с buy-and-hold.
- [ ] Unit-тесты: генерация сетки, переворот уровня, границы диапазона,
      округления.

## M4. Исполнение и риск-менеджмент (3–4 дня)

**Готово, когда:** хаос-тест (случайные отказы API, обрыв WS) не приводит к
дублям ордеров или рассинхрону; kill-switch срабатывает < 5 с.

- [ ] `execution/engine.py`: цикл «желаемые ордера (от стратегии) − реальные
      (от биржи) → минимальный набор create/cancel». Никогда не отправлять
      ордер, если состояние не сверено.
- [ ] `risk/manager.py` — правила ДО отправки любого ордера:
  - max капитал бота, max размер позиции в базовом активе;
  - дневной лимит убытка → автостоп (cancel-all + пауза до ручного запуска);
  - N ошибок API подряд → автостоп;
  - kill-switch: команда из Telegram и SIGTERM → `cancel_all()` + фиксация
    состояния + выход.
- [ ] `exchange/private_ws.py`: подписка на `order`, `execution`, `wallet`;
      обрыв → reconnect с ресинком через REST (`reconcile`).
- [ ] Graceful shutdown в `main.py` (SIGTERM из Docker).

## M5. Мониторинг (2–3 дня)

**Готово, когда:** все события уходят в Telegram, бот отвечает на команды.

- [ ] `monitoring/telegram.py`: алерты (fill, автостоп, рассинхрон, дрейф
      времени, остаток rate limit, обрыв WS) + команды `/status` (позиция,
      PnL, открытые ордера), `/stop` (kill-switch), `/pause`.
- [ ] `monitoring/health.py`: heartbeat-файл/эндпоинт для healthcheck Docker;
      структурированные логи (JSON) с ротацией, **без ключей и подписей**.
- [ ] Ежедневный отчёт в Telegram: сделки за день, PnL, сверка баланса.

## M6. Прогон на Demo Trading (2–4 недели календарно)

**Готово, когда:** ≥2 недели непрерывной работы на `api-demo.bybit.com` без
ручных вмешательств; сверка учёта — ноль расхождений.

- [ ] Создать demo-UID и ключи (мейннет-аккаунт → Demo Trading → API).
- [ ] Запуск в Docker на целевом VPS (та же инфраструктура, что и прод).
- [ ] Сценарии обязательной проверки: перезапуск контейнера, обрыв сети 10
      минут, ручная отмена ордера на бирже (бот должен заметить через
      reconcile), выход цены из диапазона.
- [ ] Помнить об отличиях demo: ордера живут 7 дней, лимиты не повышаемые.
- [ ] По итогам — тюнинг параметров сетки на свежем бэктесте.

## M7. Продакшен-запуск (2–4 недели, ступенчато)

**Готово, когда:** бот торгует целевым капиталом, метрики совпадают с demo.

- [ ] Чек-лист безопасности из PLAN.md §3 закрыт на 100%: RSA-ключ,
      IP-whitelist, права Read+SpotTrade (без Withdrawal), отдельный
      субаккаунт, 2FA, секреты только в env/secret-store.
- [ ] Canary: 1–5% целевого капитала, ≥2 недели.
- [ ] Ступени масштабирования: ×2 капитала не чаще раза в неделю и только
      при совпадении фактических метрик с бэктестом.
- [ ] Операционный регламент: кто и как жмёт kill-switch, план отката
      (стоп → cancel-all → ручное закрытие позиции), еженедельная сверка PnL.

## M8. v2 — расширения (после стабильного прода)

- DCA-модуль как вторая реализация `strategy/base.py` (ядро уже готово).
- Несколько торговых пар (изолированные инстансы стратегии, общий rate-limiter).
- Трейлинг границ сетки; веб-дашборд (FastAPI) поверх журнала SQLite.

## Принципы, которые не нарушаем

1. Биржа — источник истины: любое расхождение решается в её пользу.
2. Ни один ордер не уходит без проверки риск-менеджера.
3. Ключи не появляются в git, логах и конфигах репозитория.
4. Каждая веха закрывается тестом/прогоном, а не «на глаз».
5. Реальные деньги — только после M6 без расхождений.
